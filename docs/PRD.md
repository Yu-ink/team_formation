# PRD — 팀 프로젝트를 위한 팀 편성 웹 앱

## 1. 배경과 목표

팀 프로젝트 팀을 교수가 일일이 짜면 학생의 역할(기획, 개발, 디자인 등)이 한 팀에 몰리거나 빠지기 쉽다.
이 앱은 **학생이 스스로 팀에 지원하고 팀원이 투표로 받아들이는 방식**으로 팀을 만들고,
모집 마감 뒤 **남은 학생은 AI가 배정하되 앱이 규칙으로 검사**해서 모든 팀이 규칙을 지키게 한다.

| 목표 | 성공 기준 |
|---|---|
| 규칙을 지키는 팀 구성 | 확정한 팀이 모두 2~4명, 주 역할 중복 없음, 기획자·웹 프로그래머를 서로 다른 학생이 맡음 |
| 여러 사람이 동시에 써도 맞는 결과 | 다른 학생의 지원·투표가 5초 안에 내 화면에 보이고, 마지막 자리에 두 명이 동시에 들어가도 한 명만 기록됨 |
| AI가 실패해도 배정이 끝남 | 1·2·3차 모델이 모두 실패해도 앱이 직접 규칙을 지키는 배정을 찾음. 전체 대기 시간 6분 이내 |
| 자동 채점 가능 | 공고 2.7절 화면 이름 표의 key를 모두 지킴, 결과 안내가 승인·대기·거절·막힘으로 시작 |

난이도 선택: **어려움** — 공고 3장 표의 모든 기능을 "어려운 해결"로 만든다.

## 2. 사용자

| 사용자 | 하는 일 |
|---|---|
| 가상 학생(명단 CSV의 학생) | 학번·비밀번호(1234)로 로그인 → 팀 목록과 팀원의 주/보조 역할 보기 → 팀에 지원 → 내 팀에 들어온 지원에 찬성/거부 |
| 관리자(교수) | 학번 `admin`으로 로그인 → 명단 CSV와 팀 수로 처음 상태 만들기 → 모집 마감 → AI 배정 → 배정안 확인 후 확정 |

화면을 조작하는 사람(과제할 때는 수강생, 채점할 때는 채점자)이 가상 학생과 관리자로 번갈아 로그인한다.

## 3. 기능 요구 사항

### 3.1 로그인
- 학번 + 비밀번호. 비밀번호는 bcrypt 해시로만 저장(학생마다 다른 소금값).
- 관리자 계정은 앱이 시작할 때 비밀 값 `ADMIN_PASSWORD`로 만들거나 비밀번호를 갱신. 명단을 다시 올려도 남음.
- 비밀번호가 틀리면 로그인되지 않고, 학번만으로는 들어갈 수 없음. 관리자 기능은 서버에서 관리자인지 다시 확인.

### 3.2 명단 올리기(관리자)
- CSV(UTF-8, BOM 있어도 됨: `utf-8-sig`) 열: `student_no,name,main_role,sub_roles`. 보조 역할은 `;`로 구분, 없으면 빈칸.
- 역할은 6개(기획자, 웹 프로그래머, 프론트엔드 디자이너, 테스터, 보고서 작성자, 발표자)만 허용. 틀리면 "막힘: 명단 오류 …".
- 올리면 지원·투표·팀원·마감 표시를 모두 지우고 학생과 빈 팀(팀1…팀N)을 만든다.

### 3.3 팀 규칙(공고 2.3절)
- 확정한 팀은 2~4명, 빈 팀 없음.
- 한 팀 안에서 **주 역할**이 같은 학생 2명 이상 금지.
- 모든 팀에 기획자와 웹 프로그래머를 **서로 다른 학생**이 맡아야 함(주 또는 보조 역할). 한 학생이 둘 다 가능해도 하나로 셈.

### 3.4 지원과 투표(공고 2.4절)
| 상황 | 결과 |
|---|---|
| 빈 팀에 지원 | 승인(바로 팀원) |
| 팀원이 있는 팀에 지원 | 대기 → 그 순간의 팀원 모두가 투표 |
| 모두 찬성 | 승인 직전에 규칙을 다시 검사해 통과하면 승인, 어기면 거절 |
| 한 명이라도 거부 | 바로 거절 |
| 막힘(지원을 아예 받지 않음) | 팀이 꽉 참 / 같은 주 역할의 팀원이 있음 / 이미 팀이 있음 / 결과를 기다리는 지원이 있음 / 모집 마감 / **필수 포함 역할을 맡을 학생의 자리가 모자람** |
| 투표 바꾸기 | 불가(한 번 투표하면 "내 투표: 찬성"으로 보임) |

- 필수 포함 역할 자리 계산: 지원자가 들어간 뒤 남는 자리 수 < 그 팀에서 아직 못 채운 필수 포함 역할 수 → 막힘.

### 3.5 마감과 배정(공고 2.5절)
1. 모집 마감: 대기 중인 지원은 거절, 1명뿐인 팀의 학생은 팀에서 빠짐.
2. AI 배정: 팀이 없는 학생만 기존 팀에 넣음(이미 팀이 있는 학생은 옮기지 않음).
3. 배정안 검사 5가지: 빠짐없이 배정 / 한 학생 한 팀 / 모든 팀 2~4명 / 주 역할 중복 없음 / 필수 포함 역할 충족.
4. 1차 → 2차 → 3차 모델. 모델마다 **120초 전체 대기 시간**을 재서 끊고 다음 모델로. 빈 응답·오류·HTTP 429·형식 오류·검사 실패도 실패.
5. 3차까지 실패하면 **앱이 모든 경우를 따져(백트래킹) 규칙을 지키는 배정을 찾음**.
6. 규칙을 지키는 배정이 아예 없으면 AI를 부르지 않고 "규칙을 지키는 배정이 없음"과 이유(예: 팀3에 웹 프로그래머를 맡을 학생이 없음)를 보여 줌.
7. 검사를 통과한 배정안(이름, 역할, 배정된 팀)을 관리자에게 보여 주고, 확정하면 DB에 저장.

### 3.6 화면
- 학생: 팀 목록(내 팀 표시 "🟢 내 팀", 팀이 없으면 "아직 팀이 없음"), 팀마다 지원 단추, 내 팀에 들어온 지원과 찬성/거부 단추.
- 이미 팀이 있거나 결과를 기다리는 지원이 있거나 마감이면 지원 단추 비활성.
- 관리자: 명단 올리기, 마감, AI 배정 진행 안내(**몇 차 모델의 응답을 몇 초째 기다리는지**), 배정안 표, 확정, 팀 현황, 팀이 없는 학생.
- 결과 안내(`result`)는 "승인/대기/거절/막힘: 이유" 꼴.
- 화면 key는 공고 2.7절 표 그대로(부록 표: `docs/구현 계획.md` 4장).
- 시각은 한국 시간으로 보여 줌(서버는 UTC).

## 4. 비기능 요구 사항
- **다른 사람의 변경 보기**: `st.fragment(run_every=5)`로 팀 목록·투표 영역만 5초마다 저절로 다시 그림.
- **동시성**: 지원·투표·승인은 팀 행을 `SELECT … FOR UPDATE`로 잠근 트랜잭션에서 처리 → 같은 팀에 대기 중인 지원이 여럿이어도 투표가 끝난 순서대로 하나씩 처리. `tf_members (team_id, slot_no)` 기본 키와 `student_id` 유일 제약으로 마지막 자리에 먼저 도착한 학생만 기록.
- **성능**: DB 연결 풀을 한 번만 만들어 다시 씀(화면 한 번 그릴 때 연결 1개, 질의 6번).
- **보안**: 키·DB 주소·관리자 비밀번호는 `.env`/Streamlit Secrets에만. 화면·로그에 출력하지 않음. Supabase Data API로 표에 접근하지 못하게 RLS를 켬.
- **DB 일시정지 막기**: GitHub Actions(외부 예약 서비스)로 매일 두 번 DB에 질의.
- **AI 전체 시간**: 최대 120초 × 3 + 앱 직접 배정(1초 미만) → 10분을 넘지 않음.

## 5. 범위 밖
- 구글 로그인(`st.login`), 실제 학생 정보, 팀 이름 바꾸기, 투표 취소, 마감 취소.

## 6. 화면 흐름
```
로그인 ─┬─ 학생 → [팀 목록 · 지원] → [내 팀 지원 투표]  (5초마다 갱신)
        └─ 관리자 → 명단 올리기 → 모집 마감 → AI 배정(1→2→3차→앱) → 확정
```
